# 大手企業の公開デザイン資料：仕様書の書き方調査

調査日: 2026-09-25 / 状態: 調査結果。新UIの確定仕様ではない。

## 調査の結論と資料の扱い

今回の公開Web調査では、個別製品の社内デザイン仕様書の完全版は確認できなかった。以下は企業公式のデザインシステム・ゲーム向けガイドラインであり、社内仕様書とは区別する。全文転載ではなく、書式と内容の要約を記録する。

推奨する組み合わせは、IBMの部品記述、Visaの状態定義、Atlassianの構造・挙動記述、Microsoftのゲーム向け検証観点。業務ソフトの配色やレイアウトをゲームに持ち込むための資料ではない。

## 1. IBM — Carbon / Notification

公式: https://carbondesignsystem.com/components/notification/usage/

資料の種類: 通知コンポーネントの公開仕様・利用ガイド。

確認した構成: Usage / Style / Code / Accessibilityの分離。Usageでは概要、用途、種類、構成要素、文言、種類別の配置・サイズ・消去条件、共通挙動を記述している。検証状況とデモもある。

書き方の特徴: 見た目だけでなく、どの状況にどの種類を使うかを説明し、ユーザーが次に取る行動まで扱う。

大喜利ダイスへの応用案: 手番案内・採点待ち・通信失敗・到着・優勝を「通知」として一括にせず、表示目的、入力を止めるか、閉じ方、再表示の必要性を定義する。企業側の通知時間をそのままゲーム演出時間にはしない。

## 2. Visa — Product Design System / Button・States

公式:
- https://design.visa.com/components/button/usage/
- https://design.visa.com/base-elements/states/usage/

資料の種類: ボタンの利用ガイドと共通状態仕様。

確認した構成: ボタンの重要度・用途別の使い分けと、良い例／避ける例。状態は通常、ホバー、押下、フォーカス、選択、無効、読み取り専用、エラーなどを区別する。すべての部品が全状態を持つわけではない。

書き方の特徴: 部品ごとの仕様と全体共通の状態ルールを分離している。

大喜利ダイスへの応用案: 「回答送信」「移動候補」「全体マップ」に対して、使用可能条件と各状態の見た目・操作を表で書く。タッチではホバーに依存しない。原典のdpをWebのCSS pxに無条件変換せず、対象端末で押しやすさを検証する。

## 3. Atlassian — Design System / Panel

公式: https://atlassian.design/components/panel/usage

資料の種類: パネルの公開コンポーネント仕様。調査時点ではBeta表示。

確認した構成: Usage、Parts、Header types、使用・非使用条件、Behavior、Best practices。構成要素の任意・必須、開閉、戻る操作、操作数、余白などを具体化している。

書き方の特徴: 自由に変更できる領域と統一すべき領域を分け、操作後に何を保持するかまで明示する。

大喜利ダイスへの応用案: お題・回答・結果の共通ウィンドウについて、見出し、本文、補助情報、操作領域を分解する。手番や画面が変わった時のフォーカス、入力内容、マップ位置の扱いも書く。Atlassianの右側パネル配置自体は採用理由にならない。

## 4. Microsoft — Xbox Accessibility Guidelines

公式:
- https://learn.microsoft.com/en-us/xbox/accessibility/guidelines
- https://learn.microsoft.com/en-us/gaming/accessibility/xbox-accessibility-guidelines/101
- https://learn.microsoft.com/en-us/gaming/accessibility/xbox-accessibility-guidelines/102
- https://learn.microsoft.com/en-us/xbox/accessibility/xbox-accessibility-guidelines/103

資料の種類: ゲーム開発・評価向けの公開ガイド。個別作品のUI仕様書ではない。

確認した構成: 目的、概要、適用範囲を判断する質問、基礎情報、対象箇所、実装指針、実例、プレイヤーへの影響、参考資料。文字、コントラスト、入力、フォーカス、制限時間、動きなどを別項目として扱う。

書き方の特徴: 「なぜ必要か」「どこに適用するか」「何を確認するか」がつながる。掲載例の一部分が良い実例でも、その画面全体が全指針を満たすとは限らないと説明している。

大喜利ダイスへの応用案: 地名・お題・回答・金額・残り時間を別々に評価し、実サイズで読めるか、色や音だけに意味を依存していないかを確認する。コンソール向けの文字サイズ値をブラウザにそのまま転用しない。

## 横断して得られた記述方針

以下は資料を基にした本プロジェクト向けの提案であり、各社共通の社内テンプレートではない。

1. 目的・対象者・利用場面を先に書く。
2. 画面単位とコンポーネント単位を分ける。
3. 構成図には番号を付け、各要素の役割と表示条件を対応させる。
4. 通常状態だけでなく、待機、無効、失敗、長文、人数増加を記述する。
5. 見た目と動作を分離し、色・余白・文字を共通トークンで参照する。
6. 良い例／避ける例と、その理由を添える。
7. 完了条件を第三者が再現できる操作と結果で書く。
8. 参考資料、観察事実、自分たちの判断、未決事項を区別する。

## 既存仕様書との差分

既存の `docs/superpowers/specs/2026-07-22-tokyo-map-visual-redesign-design.md` はSVGレイヤー・配色・カメラを具体化している。一方、UI全体を作り直すには次の設計が必要。

- 端末・画面向き・1〜4人・入力機器の想定。
- 各フェーズで最優先に読ませる情報。
- お題・入力・結果・移動・チャレンジを通じた画面構造。
- 長文、日本語IME、ソフトウェアキーボード、通信待ち・失敗。
- 文字、ボタン、パネル、プレイヤー色、意味を持つ色の共通ルール。
- 演出の開始・終了、操作可能になる時点、短縮表示。
- モック画面と受け入れ条件の対応。

以前提案した「上部HUD＋下部ウィンドウ」「クリーム＋空色」は候補に戻す。今回の調査をもって採用決定にはしない。

## 調査上の限界

- Adobe Spectrumは対象ページがJavaScript依存で本文取得できず、具体的な仕様抽出の根拠から外した。
- 国内企業の公式公開記事も検索したが、今回の用途に直接使える個別製品の完全な仕様書は確認できなかった。
- 公開資料の事実確認であり、各社の非公開制作工程や効果を推定していない。
