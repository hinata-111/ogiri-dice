# 大喜利ダイス：UIデザイン仕様書の記入テンプレート

状態: 調査から作成した書式案。仕様を確定した文書ではない。

根拠: [公開資料調査](2026-09-25-design-spec-writing-research.md) / [ゲーム参考調査](2026-09-25-game-ui-reference-research.md)

## 文書の分け方

仕様本体は、体験方針 → 画面・状態 → 共通部品 → 表現 → 検証の順に書く。実装ファイル分割と作業順序は別の実装計画に置く。

| 章 | 記入する内容 | 完了の目安 |
|---|---|---|
| 1. 目的・範囲 | 解決する課題、対象画面、対象外 | UI変更とルール変更が区別される |
| 2. 利用条件 | 対象端末、画面向き、人数、入力方法、初見／再訪 | 判断に使う前提が明示される |
| 3. デザイン原則 | 原則、理由、良い例、避ける例 | 意見が割れた時の判断に使える |
| 4. 参考と独自性 | 作品・資料、参考箇所、採用理由、本作への変更 | 見た目だけの模倣にならない |
| 5. 画面一覧・遷移 | 全フェーズ、表示内容、操作、遷移条件 | 正常・待機・失敗に抜けがない |
| 6. 画面構成 | 端末別の注釈付きレイアウト、優先順位 | 何を最初に見るか説明できる |
| 7. 部品仕様 | 構成、状態、操作、文言、例外 | 通常以外の描画も決められる |
| 8. 表現の共通ルール | 色の役割、書体、サイズ階層、余白、枠、影、アイコン | 全画面で使い回せる |
| 9. 動きと音 | 開始条件、順序、時間、操作制限、スキップ、音なし時 | 実装と検証が同じ解釈になる |
| 10. 読みやすさと入力 | 長文、拡大、色覚、動きの軽減、IME、フォーカス | 例外でも操作できる |
| 11. 受け入れ条件 | 操作手順、期待表示、検証端末、記録 | 合否を再現可能に判断できる |
| 12. 決定記録 | 決定日、理由、変更履歴、未決事項、参照版 | 仮案と決定済みを区別できる |

## 各画面の記入カード

- ID・画面名:
- プレイヤーの目的:
- 表示開始条件／終了条件:
- 最優先情報／常時情報／補助情報:
- 構成図と要素番号:
- 各要素の表示条件:
- 主操作／補助操作／無効な操作:
- タッチ・マウス・キーボード操作:
- 次の画面・状態:
- 人間手番とCPU手番の差:
- 長文・小画面・キーボード表示時:
- 待機・失敗・再試行時:
- 読み上げ・フォーカス:
- 演出と音:
- 受け入れ条件:

## 各部品の記入カード

- 名前と役割:
- 使用する場面／使用しない場面:
- 構成要素（必須・任意）:
- 種類と重要度:
- 通常／選択／フォーカス／押下／無効／処理中／失敗:
- 文字数、折返し、省略、数字の書式:
- サイズ・余白・色・枠・文字のトークン:
- 操作領域と操作方法:
- 良い例／避ける例と理由:
- 検証ケース:

該当しない項目は「該当なし」と理由を書く。未決の項目を確定値のように記載しない。

## 書き方の具体例（未承認の仕様例）

### 例：移動候補

曖昧な記述: 「分岐を分かりやすくする」。

具体的な記述例:

- 移動可能な候補を、地図上の矢印と操作ボタンで同じ記号・名称に対応付ける。
- 同じ画面に同一ラベルだけの選択肢を複数置かない。
- 方面名を使う場合、表示対象となる拠点の選定規則を別途定義する。隣接ノード名を無条件に方面名としない。
- ホバー以外に、キーボードフォーカスでも対応する進路を確認できるようにする。
- 1回の決定が何歩に対応するか、押しっぱなしや連打の扱いを定義する。
- 合否例: 新宿の3分岐を表示し、各ボタンから対象経路を一意に識別できる。既存の不正遷移無視の性質を維持する。

### 例：回答画面

曖昧な記述: 「残り時間を目立たせる」。

具体的な記述例:

- お題と同時に残り秒数を表示し、バーだけに依存しない。
- 秒数の丸め方、警告開始の閾値、0秒時の入力処理を明示する。
- 回答制限時間はゲームルールを参照し、UI仕様内に別の値を定義しない。
- IME変換確定と送信を区別する。
- キーボード表示時もお題・残り時間・入力・送信の配置を検証する。
- 合否例: 日本語変換中のEnterで送信されず、変換確定後に明示的な操作で送信できる。

## デザイン着手前に決める順序

1. 主な遊び方：PC中心か、スマートフォン中心か。1台を囲む遊びか。
2. 各フェーズの主役：地図、お題、回答、対戦状況の優先順位。
3. 上記を満たす画面構成案を比較する。
4. 文字・枠・配色・アイコンの方向を比較する。
5. 代表画面を、通常・長文・小画面で確認する。
6. 状態・例外・受け入れ条件を埋め、仕様を確定する。

## 検証マトリクスの候補

画面幅や高さの数値は対象端末の合意後に確定する。

- 1人／4人、短い名前／長い名前。
- PC横長／スマートフォン縦長／ソフトウェアキーボード表示。
- 短いお題／長いお題、空回答／長い回答。
- 採点成功／待機／通信失敗／フォールバック。
- 分岐／行き止まり／目的地画面外／全体表示。
- 通常回答／青チャレンジ／赤チャレンジ／到着／優勝。
- タッチ／キーボード、音なし、動きを軽減した表示。

## 実装への引き渡し

画面と状態の対応を既存reducerへ照合する。新しい確認待ちやタイマー開始方式が必要なら、純粋な見た目変更に含めず状態遷移の変更として明記する。`game/` の変更はテスト先行とし、UIは状態の描画とアクション発行を担う。

既存仕様の「プロシージャルSVGのみ」を今回も維持するかは、アセット方針の決定項目として明示する。無断で方針を切り替えない。
