## 1. 目的と成功条件

目指す体験は「東京の街を旅しながら、その場で生まれたボケをみんなで楽しむ」。各場面で、見る対象と次の操作が一つに絞られる画面を作る。

1. 移動中は、自分の位置・目的地・進める道を理解できる。
2. 回答中は、お題・残り時間・入力に集中できる。
3. 採点後は、誰のどんな回答だったかを読んでから、その成果を理解できる。
4. 色や装飾がなくても、手番・選択肢・成功・失敗を識別できる。
5. PCの大きな画面とスマートフォンの小さな画面で、情報を並べ替えて同じ遊びを成立させる。

「桃鉄風」の評価を単なる色や太枠の類似で行わず、地図を見て進路を判断する分かりやすさ、旅の目印、手番と報酬の理解で行う。

## 2. 維持するゲーム内容

数値の正本は `game/rules.ts`。以下は調査時点の契約で、UI側に重複したゲーム定数を作らない。

| 項目 | 維持する内容 |
|---|---|
| 人数 | 1〜4人、人間・CPUの組み合わせ |
| 回答 | 15秒、採点は1〜6点。通常のお題の点数が移動数になる |
| 時間切れ | 未送信回答は採用せず1点。入力途中の文章を勝手に送信しない |
| 移動 | 隣接マスへ1歩ずつ。来た道には原則戻れず、行き止まりでは戻れる |
| 目的地 | 劇場・テレビ局。通過でも到着し、残り移動数を終了する |
| 到着報酬 | 30万円、到着回数を加算、次の目的地を抽選 |
| 青チャレンジ | 追加回答の点数×3万円を獲得。移動はしない |
| 赤チャレンジ | 目標1〜4点。未達の差×3万円を失い、達成なら増減なし |
| 所持金 | 初期10万円、下限0円 |
| 勝利 | 手番終了時に100万円以上。全員30ターンで終了する上限も維持 |
| 順位 | 所持金、同額なら到着回数。両方同じなら同順位として表示 |
| 評価器 | Geminiとモックの差し替え契約、通信失敗時のフォールバック |

地名・拠点ID・接続・マス効果はゲームデータとして維持する。画面上の座標、道路や建物の形、背景素材は新規設計する。座標変更は生成スクリプトから再生成し、map.jsonを直接編集しない。

## 3. 利用環境の設計仮定

今回の案では、PC・タブレットの1台を囲むプレイを主対象とし、スマートフォン縦画面を同等の機能を持つ別レイアウトで扱う。オンライン対戦・各人の別端末入力・ゲームパッド専用操作は今回の範囲外。

| 区分 | レイアウト判定 | 検証する代表サイズ（CSS px） |
|---|---|---|
| ワイド | 幅960以上、かつ高さ600以上 | 1280×720、1440×900、1024×768 |
| コンパクト | 上記以外 | 390×844、360×640、844×390 |

これはユーザーから指定された端末ではなく設計仮定。拡大表示、キーボード表示で利用領域が狭まる場合はコンパクト構成へ移る。ページ全体のスクロールは禁止せず、操作不能になる固定高さを避ける。

## 4. 方向性の比較と今回の提案

| 方向 | 長所 | 弱点 |
|---|---|---|
| 旅のボードゲーム中心 | 地図と目的地が常に分かる | お題・回答に割ける面積が少ない |
| お笑い番組中心 | 回答と採点が盛り上がる | 東京を巡る意味が背景化する |
| 場面ごとに主役を切り替える | 移動・回答の両方を十分に見せられる | 切替と共通表現の設計が必要 |

本書の提案は3番目。作品の仮コンセプトを「東京ボケめぐり — 街が舞台の大喜利旅」とする。製品名「大喜利ダイス」は変更しない。

参照の役割は、桃鉄から地図・地名・進路、マリオパーティから目印と成果の強調、Quiplashから回答を読む場面の分離。参考作品の素材・ロゴ・キャラクターは用いない。

## 5. デザイン原則

| 原則 | 採用する例 | 避ける例 |
|---|---|---|
| 主役は一つ | 回答中はお題と入力を大きくする | 小さいお題の背後で地図が動く |
| 操作には結果を予告する | 「1マス進む」「4マスの移動へ」 | すべて「OK」「すすむ」 |
| 地図は判断の道具 | 経路・次のマス・目的地を分離 | 建物の陰にマスや矢印が隠れる |
| 状況変化を読める | 獲得額と確定後の金額を併記 | 数字だけ瞬時に置き換わる |
| 読む時間を奪わない | 結果は明示操作で進む | 長い回答の表示を時間だけで閉じる |
| 同じ意味は同じ表現 | プレイヤー番号と固有色を全画面で共用 | 赤が手番・エラー・目的地を兼ねる |

## 6. 新しいビジュアル言語

### 6.1 全体の表現

明るい紙の案内板、切符、劇場の見出しをモチーフにする。画面枠は直線を基本に控えめな角丸、重要数値は大きく、説明は落ち着いた濃色。色数と装飾密度を抑え、地図上のプレイヤーと進路に色を集める。

旧UIの濃紫パネル、発光、絵文字主体のコマ、アイソメ菱形マス、既存SVG建物は再利用しない。過去に提案したクリーム＋空色案の継承を理由に色を決めない。

### 6.2 配色トークン案

| 役割 | 値 | 用途 |
|---|---|---|
| paper | #F7F4EB | 画面の基調面 |
| surface | #FFFFFF | お題・入力・案内の面 |
| ink | #182D3A | 本文・輪郭 |
| muted-ink | #53616A | 補助文。薄い透明度で代用しない |
| action | #173E50 | 主操作の面、白文字 |
| destination | #F2C14E | 目的地の標識、濃色文字 |
| chance | #126B98 | 青チャレンジ、白文字＋「獲得」表記 |
| risk | #A73743 | 赤チャレンジ、白文字＋「失点注意」ではなく「減額の可能性」表記 |
| success | #236B4A | 獲得・達成、白文字 |

値はこの案での初期指定。全組み合わせのコントラストを検証済みではない。実装前のビジュアル確認で通常文字4.5:1、重要な操作輪郭3:1を目標に測定し、不足する組み合わせは調整する。背景イラストの上に文字を直接重ねない。

### 6.3 文字・寸法

- 日本語書体はNoto Sans JPを新規採用候補とする。400・700・900の3ウェイト。配布時にライセンスを同梱し、実装時に入手元を確認する。フォールバックはOSの日本語ゴシック。
- 本文16px・行高1.6、補助14px・1.5、見出し24px・1.35。お題はワイド32px／コンパクト24px、回答は28px／22px。長文でも本文を16px未満に縮めない。
- 結果数値は64px／48px。数字は桁幅を揃える。金額は「10万円」、マス数は「あと4マス」、周は「3 / 30ターン」と役割を明記。
- 余白は4・8・12・16・24・32・48px。本文パネルは24px／16pxの内余白。
- 基本角丸12px、入力8px、番号バッジのみ円形。輪郭2px、選択状態3px。影は下方向4pxの控えめなもの一種。
- 主操作は高さ52px以上、他の操作領域も48×48px以上。これは本作の設計値で、企業資料のdpを転記したものではない。

### 6.4 新規素材一覧

| 素材 | 新しい表現 | 形式案・制作条件 |
|---|---|---|
| 東京マップ | 真上に近い2Dイラスト。地区を島状の面、道を連続した帯として描く | 新規SVG。地理はデフォルメ、接続関係を優先 |
| 建物 | 劇場は幕、テレビ局はアンテナ、駅は改札を共通シルエットに | 新規ベクターシンボル。拠点ごとに独自の差分 |
| コマ | 旅行かばん型の独自コマにプレイヤー番号を付ける | 4種の新規SVG。48px基準で判別可能 |
| マス | 上から見た角丸四角、青は＋、赤は！、通常は小点 | 新規SVG。コマとの重なり時も輪郭を残す |
| 目的地 | 地名付きの旗型看板と輪郭リング | 新規SVG＋HTML文字。画面外では方向標識 |
| アイコン | 地図・戻る・音・移動・送信・賞金の統一線画 | 24px基準、2px線。操作には文字ラベルを付ける |
| タイトル絵 | 東京の街を横断する旅行かばんと劇場 | 新規イラスト。必要に応じWebP/AVIF、UI文字は画像に焼き込まない |
| 案内役 | 固有キャラクターは必須にせず「旅の案内」の名札 | 初期版では文字と小さな独自アイコン |

仕様上はSVGとラスター画像の併用を認める。生成画像を使う場合も最終UI部品の寸法・文字・操作状態は別途作る。素材が未制作の段階で「完成したデザイン」とは呼ばない。

## 7. 画面構成

### 7.1 移動画面

ワイド構成。地図と操作領域を重ねず、固定4:3の地図を切り抜く方式は採らない。

```text
┌ 現在の手番・所持金 ─────── 目的地・到着賞金 ─┐
│                                              │
│        東京マップ                  対戦状況   │
│   自分のコマ・候補A/B/C             1〜4人     │
│   目的地・選択中の道                           │
│                                              │
├ 今回あと4マス ─ 選択した進路の説明 ──────────┤
│ [候補A] [候補B] [候補C]          [1マス進む]  │
└──────────────────────────────────────────────┘
```

- 外余白24px。上部帯80px、下部操作領域は内容に合わせて伸びる。対戦状況は幅216px、地図の外に置く。
- コンパクトは上部に手番と目的地、中央に地図、下部に候補と決定。対戦状況は「順位を見る」で展開する。閉じた時も自分の所持金は表示。
- 「今回あと4マス」と「目的地まで最短7マス」は別ラベル。移動中の距離は合法な次の一歩を起点に、戻り制約を含む状態グラフで算出する。到達不可なら「経路なし」、現在目的地なら0。
- 地図はドラッグと＋／−で探索できる。「現在地」「目的地」「全体」の3操作を設ける。地図を見るだけでは移動しない。
- 全体表示では全プレイ可能ノードと地名枠が地図領域内に収まる。読めない時はズームでき、目的地名・距離は画面外の情報枠で読める。
- 装飾の外縁ではなくプレイ可能範囲から全体表示倍率を決める。端末の縦横比と操作領域の実寸を使う。

### 7.2 回答画面

```text
┌ プレイヤー2の番 ─ 通常のお題 ─ あと15秒 ┐
│                                         │
│             お題の文章                  │
│                                         │
│  回答入力                               │
│  入力例ではなく「回答を書く」のラベル    │
│                          0 / 100        │
│                          [回答を送る]   │
└─────────────────────────────────────────┘
```

- 地図の代わりに静かな紙面と、その手番の現在地名を表示。地図探索・順位展開は制限時間中に出さない。
- 内容幅は最大800px。お題・時間・入力・送信を同じ領域にまとめる。
- コンパクトではキーボードの上に送信操作が収まる通常フロー。画面高が足りない時は縦スクロール可能、時間表示は上端に固定する。
- お題は省略しない。入力は複数行表示可能なテキスト欄、100文字上限。Enterは改行、送信はボタンまたはCtrl/Cmd＋Enter。IME変換中は送信しない。
- 100文字は現行HTML maxlengthと同じUTF-16コード単位として扱い、カウンタと制限を一致させる。入力中の合成文字を途中で破壊しない。文字単位の変更は別途ルールとして検討する。

### 7.3 結果画面

- 上から「誰の回答か」「お題」「回答文」「点数と効果」「短い審査コメント」「次の操作」。回答文が文章の主役。
- 回答・お題は省略しない。長い場合は本文領域を縦にスクロールできる。操作は本文を隠さない位置に置く。
- 通常は「4点 / 6点」「4マス進める」、チャレンジは「獲得12万円」「確定後22万円」など、行動・金銭の効果を明示。
- 現在の金額が未適用の場合は「確定後」と表示。到着報酬はすでに適用済みなので「獲得済み」と区別し、二重加算の演出をしない。
- 時間切れは「時間切れ・未送信」「今回は1点」。空白の吹き出しを作らない。

## 8. 画面・状態・操作の一覧

| ID / 画面 | 入る条件 | 主情報と操作 | 終了・次の状態 |
|---|---|---|---|
| S01 タイトル | 起動／再スタート | 新規タイトル絵、遊びの1文説明、「旅をはじめる」「遊び方」 | 設定へ |
| S02 参加者設定 | タイトルから | 1〜4人の新規参加者カード、名前、人間/CPU、CPUの性格、ルール要約 | 「このメンバーで出発」で開始 |
| S03 手番案内 | 開始時／前手番終了 | 現在地・目的地・手番。「お題を開く」、地図・順位の確認 | 人間の開始操作でお題を抽選・表示 |
| S04 回答 | お題を開いた時 | 通常/青/赤の目的、お題、15秒、入力、送信 | 送信で採点、時間切れで結果 |
| S05 採点待ち | 送信後 | 送信した回答を読み取り専用表示。「審査中」 | 評価器の結果でS06 |
| S06 採点結果 | 評価完了／時間切れ | 回答、点数、効果、コメント。通常は「移動へ」、チャレンジは「結果を確定」 | 移動または手番終了 |
| S07 移動 | 通常結果の確定 | 候補を選択して「1マス進む」。残り歩数と経路 | 次の1歩／到着／マス効果／手番終了 |
| S08 チャレンジ案内 | 青赤に停止 | 青は獲得式、赤は不足による減額の説明。「挑戦する」 | お題・赤の目標値を確定してS04 |
| S09 到着 | 目的地に入った時 | 場所・獲得済み賞金・所持金。「次へ」 | 勝敗判定、次の目的地、次手番 |
| S10 最終結果 | 勝利または上限 | 勝者/同順位、順位、到着回数、ベスト回答。「もう一度遊ぶ」 | タイトルへ |

設定の名前は10文字上限、空欄は「プレイヤーN」を採用。入力は保持して戻れるようにする。人数を減らす操作は対象カード内に名前付きのラベルを持ち、最後の1人は削除不可。CPUのみの設定も許容する。

手番開始前に次のお題本文を表示しない。目的地が変わった場合はS03の目的地部分に「新しい目的地」と表示する。初回だけ「お題に回答→点数分進む→目的地で賞金」の3段階説明を折り畳み可能に表示する。

### 8.1 人間とCPU

- 人間の手番案内・結果・チャレンジ案内・到着は明示操作で進む。
- CPUは手番案内を1.2秒表示して開始し、自動回答・自動移動する。生成中は人間用タイマーや入力欄を出さない。
- CPU結果は回答と採点を表示した後、全員CPUなら4秒で自動進行。人間が1人以上いる対戦では「次へ」を待ち、読む時間を確保する。
- CPUチャレンジ案内・到着は、人間混在時は「次へ」を待つ。全員CPU時のみ2秒で進める。
- 自動進行を待つ画面は「自動進行を止める」を持ち、停止後は「次へ」で進める。回答生成と採点の通信待ちは結果待ちであり、固定の自動進行時間を当てはめない。

### 8.2 回答タイマー

- S03/S08の開始操作によってお題を確定し、回答画面が利用可能になった時点から15秒。開始前の演出時間は含めない。
- 数字は残りミリ秒を秒へ切り上げ。5秒以下で「残りわずか」を併記し、点滅はしない。
- 期限は単調増加時計による締切で判定。バックグラウンドでも時間は進み、復帰後に締切を再判定する。再描画やキーボード表示でリセットしない。
- 同じ回答試行の送信・時間切れは一度だけ受理。締切以降の送信は時間切れ扱い。締切直前に送信が受理されれば評価中の時間切れは無視する。
- フォーカス離脱や画面サイズ変更でお題を再抽選しない。

## 9. 移動操作を作り直す

### 選択と決定

1. 合法な候補を地図上のA/B/C標識と、同じ文字の候補ボタンで表示する。
2. 候補の選択で経路・対象マスを強調し、「青マス：止まると獲得チャレンジ」などを表示する。
3. 「1マス進む」で一歩を確定する。地図のドラッグ終了や候補の選択だけでは移動しない。
4. 次の位置では選択を解除する。合法候補が1つの時だけ事前選択し、それでも決定操作を待つ。

候補の表示順は画面上の角度順とし、同角度はノードID順。表示名は「A ↗ 青マス」「B ↘ 通常マス」のように、記号・方向・種別で一意にする。次が名前付き拠点ならその地名を使う。将来の拠点を推測して方面名にしない。

キーボードはTabで候補へ、左右キーで候補を巡回、Enter/Spaceで候補を選択、決定ボタンで一歩確定。入力欄・他のダイアログにフォーカスがある時は移動ショートカットを受け付けない。

一歩の処理は現在位置と移動試行を識別して受理する。重複クリック・キーリピート・遅延イベントが次の位置で追加の一歩にならないよう、reducer側でも検証する。アニメーションの終了イベントだけに状態進行を依存させない。

### 地図の表示優先度

現在のコマ → 合法な候補 → 選択した進路 → 目的地 → 地名 → 他プレイヤー → 建物 → 背景の順で視認性を確保する。同じマスのコマは番号付きで並べ、重なりを避ける。

地図を手動で動かした後は自動追尾しない。移動を確定した時と「現在地」を押した時に追尾へ戻る。目的地が画面外なら端の方向標識を表示し、押すと目的地へ移動する。確認中に手番や状態が変わったら探索を終了し、新しい主役へフォーカスを移す。

## 10. 新規コンポーネント仕様

ここでの名前は新規UIの責務を表す。旧コンポーネントの改名・CSSの差し替えで済ませる前提にしない。

| 部品 | 必須内容 | 状態・例外 |

| PlayerBadge | 番号、名前、所持金、手番ラベル | 手番は枠と文字で示す。長い名前は2行、詳細では全文 |
| DestinationSign | 目的地名、距離、到着報酬 | 地図外でも常に同じ目的地。新目的地には一時的な文字ラベル |
| StandingsPanel | 全員の番号・名前・金額・到着回数 | 同順位を表示。閉じた後は呼出元へフォーカス |
| BoardViewport | 新規地図、コマ、候補、目的地、探索操作 | 待機中は閲覧可能、回答中は非表示、移動確定中は操作不可 |
| RouteChoice | 候補記号、方向、対象、マス効果 | 未選択・選択・フォーカス・確定中。選択とフォーカスを混同しない |

## 11. 待機・失敗・再試行

- 採点待ちは偽の進捗率を出さず、受け取った回答と「審査中」を表示する。5秒経過で「少し時間がかかっています」を追加する。通信の再試行やタイムアウトは評価器の契約に従う。
- フォールバックは「通信できなかったため、代替の採点結果です」と明示。「この結果で進む」を主操作、「再審査」を補助操作とする。AIが実際に採点したように見せない。
- 再審査は同じお題・同じ送信済み回答を使い、タイマーを再開しない。採点中の再送は不可。古い結果の遅延到着は無視する。
- 評価器が想定外に例外終了した場合も、採点待ちを永久に残さず同じ代替結果経路へ収束する。
- CPU生成待ちは「CPUが回答を考えています」。失敗時の定型回答は評価器に委ね、待ち状態を解消する。
- 盤面データ不整合など進行不能な場合はゲームを開始せず、理由と再読み込み操作を表示する。根拠のない移動先や距離を描かない。

## 12. 演出と音

| 場面 | 演出案 | 時間案 | 操作との関係 |
|---|---|---|---|
| 操作フィードバック | 面・輪郭・影の変化 | 120ms | 完了を待たず状態を伝える |
| 画面切替 | 短いフェード | 180ms | 入力締切の開始前に終了 |
| 一歩の移動 | コマを経路に沿って移動 | 220ms | この間の追加確定を受け付けない |
| カメラ追従 | 必要な距離だけパン | 最大300ms | 回答中には動かさない |
| 採点 | 回答を先に置き、点数を拡大表示 | 400ms | 人間混在では次へを自動実行しない |
| 到着 | 地名看板＋賞金表示 | 600ms | 読む内容は表示後も残る |
| 優勝 | 周囲に紙片と順位を表示 | 800ms | 操作ボタンと本文を覆わない |

動きの軽減設定ではパン・拡大・紙片をなくし、即時表示または100ms以内のフェードへ置き換える。移動の二重入力防止は軽減設定でも維持する。結果の全面フラッシュ・常時バウンスは使わない。

音は初期ミュート。設定から有効化した後のみ、決定・移動・採点・到着・優勝の短い独自効果音を使う。BGMは初期版の必須要件に含めない。音だけで残秒や成功を通知しない。効果音素材は未制作。

## 13. 読みやすさとフォーカス

- 新しい画面の見出しへフォーカスを移す。回答開始時は人間の入力欄へ移し、地図操作後のEnterが送信にならないようにする。
- 人間が押した「お題を開く」からタッチ端末でキーボードを開ける構造を優先する。実機で自動フォーカス不可なら入力欄を明確に見せ、勝手なタイマー延長で補わない。
- 結果の更新は点数と効果をまとめて通知する。毎秒のカウントダウンを読み上げ続けない。5秒と終了時だけ控えめに通知。
- 地図の候補は同等のHTML操作一覧で選べる。地図画像そのものを唯一の操作入口にしない。
- 200%拡大で入力・主操作・重要文言が欠けない。本文は縦方向だけで読める。
- タイマー中に設定や地図ダイアログを開けない。時間を止める機能は追加しない。制限時間の変更はゲームルールの別検討とする。

## 14. UI実装の境界と旧UIの撤去

### 維持する契約

ゲーム状態の正本は純TSのreducer。UIは描画とアクション発行を担う。評価器はインターフェース経由。旧Unityフォルダは引き続き参照専用で、一掃の対象に含めない。

### 新規に構成する責務

- SceneShell: ワイド/コンパクトの領域割り当て。
- Scene: 手番、回答、結果、移動、到着、最終結果の描画。
- DesignTokens: 新しい色・文字・余白・状態の正本。
- BoardRenderer: 新規素材とゲームデータから盤面を描画。
- BoardInteraction: 探索、ズーム、候補選択、操作説明。
- Presentation: フォーカス、演出、音、読み上げ。

React依存の表示部にゲームルールを複製しない。開閉・地図倍率・未確定候補は表示状態、残り歩数・確定位置・賞金・回答試行はゲーム状態として区別する。

### 状態・操作の変更が必要な箇所

| 変更 | 現行との差 | 検証内容 |
|---|---|---|
| 手番・チャレンジ開始 | 時間で開始せず人間の確認を待つ | お題確定と15秒開始が一度だけ |
| 回答試行の識別と締切 | UI更新から独立した試行ID・締切の導入 | 時間切れ競合・古い非同期結果を無視 |
| 移動確定の識別 | 位置/移動試行に紐づけた一歩の確定 | 連打・キーリピートで余分に進まない |
| 合法経路の距離表示 | 戻り制約を含める純関数を追加 | 分岐・行き止まり・到達不可 |
| CPUの画面進行 | 人間混在と全CPUで読了待ちを分ける | CPU結果で進行不能にならない |

`game/` の変更はテスト先行。まず既存ルールの回帰テストを確認し、新しい入力契約の失敗テストから変更する。

新しいUIは独立した入口で制作・検証し、完成後に旧UIのimport、コンポーネント、CSS、描画・カメラ・演出専用コード、使われなくなったアセットを参照関係に沿って撤去する。旧UIを最終成果に残さない。一方、ゲームデータ・評価器・有効なルールテストまで一括削除しない。撤去は別の実装計画で対象ファイルを列挙する。
