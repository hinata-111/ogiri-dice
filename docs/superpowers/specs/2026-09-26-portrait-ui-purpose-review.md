# 縦持ちゲームUI・目的と操作のレビュー

日付: 2026-09-26
対象: 現行本体とscenes.html。Chrome 393×852でタイトル、4人設定、手番開始、回答、通常採点、進路候補、候補選択、全体地図を操作。到着、赤マス導入、賞金結果、最終順位は実コンポーネントの固定データ見本で確認。見本の上部ナビゲーションは製品の評価に含めない。iPhone実機・初見ユーザーテストは未実施。実装は変更していない。

## 総評

基本操作は成立するが、場面の目的から設計した完成品というより、共通パネルに機能を配置した試作の印象が残る。「AIが作った」ことを外観から断定する評価ではない。具体的な原因は、全場面で似たパネル構成、汎用フォームの設定画面、描き込みの多い背景と平面的なUIの不一致、縦画面への単純な積み替えにある。美術の追加より、判断に必要な情報と主操作の関係を先に直す。

## 優先課題

### 高: 全体地図では位置関係を読み取りにくい
- 根拠: app/src/components/map/TokyoBoard.tsx:37,65,66。
- 観察: 393×852の画面で16:9の地図が中央の約221px高に収まり、上下が広く空く。地名札と4人のコマは地図に比べて大きく、新宿・中野・池袋周辺で重なる。
- 影響: 目的地までの経路と現在地を把握するという画面の目的を妨げる。
- 修正: 全体地図専用の表示を用意する。操作可能な拡大・移動、現在地/目的地の強調、縮尺に応じた地名の間引きとコマ集約。縦画面の領域を活用する。単に札を小さくして解決しない。
- 受入れ: 4人が同じ地点にいても現在地、目的地、接続経路を判別できる。

### 高: 進路を選ぶ前の比較材料が不足
- 根拠: app/src/components/map/TokyoBoard.tsx:67,72。
- 観察: 画面上の候補はA/B/Cのみ。目的地までの距離は選択後に下部へ出る。今回Aを選ぶと現在8マスから9マスになるが、選択前には比較できない。
- 影響: ゲーム上の判断が、候補を順番に押して調べる操作になる。
- 修正: 候補付近に「目的地まで○マス」とマス種別を併記。選択経路を強調し、確定は維持する。分岐でない道でも毎回二操作が必要な点は、手動移動ルールを守りつつ別途検討する。
- 受入れ: 候補を試し押しせず、距離とマスの違いを比較できる。

### 中: プレイヤー設定が汎用フォームの見た目
- 根拠: app/src/components/SetupScreen.tsx:43-69、app/src/App.tsx:44。
- 観察: CPUの性格と削除ボタンが次行に折り返し、参加者の区切りが弱い。人間/CPU/攻めるはフォーム値として並ぶだけ。名前入力へ自動フォーカスする実装もあり、設定全体を見る前にキーボードが開くリスクがある（実機での発火は未検証）。
- 修正: 色とコマを持つ参加者枠に名前・操作種別・CPU性格・削除を収める。標準設定で直ちに開始できることを主軸にし、名前編集はタップ時のみ。
- 受入れ: 誰が参加し、どれがCPUの設定か、4人でも一目で分かる。

### 中: 回答の集中状態をキーボードの有無で切り替えすぎる
- 根拠: app/src/App.tsx:160、app/src/index.cssのanswer-windowとdata-keyboard-open。
- 観察: 入力前/外付けキーボードでは地図が画面の大半、お題は下部。ソフトキーボード表示中はパネル全体へ大きく移動する。
- 修正: 回答フェーズに入った時点で、お題を安定した位置に置く。残り時間→お題→入力→送信の一方向の視線にする。地図は文脈を残す背景とし、回答時の主役にはしない。
- 受入れ: キーボード開閉でお題を探し直さない。15秒中に入力場所で迷わない。

### 中: 採点結果で回答文が主役になりすぎる
- 根拠: app/src/components/ResultOverlay.tsx:41,46。
- 観察: 長文結果では回答と講評が最上段を占め、その後に6点、+18万円、所持金、ボタンが並ぶ。お題自体は結果に表示されない。
- 修正: 点数とゲームへの効果を先に提示し、お題・回答・講評をまとまりとして下に置く。「結果を受け取る」は賞金/減額後の次動作が分かる文言へ。通常の「6マス進む！」は維持。
- 受入れ: 点数、何が起きるか、次に押すものが最初の視線で分かる。

### 中: 場面の違いがほぼ文章と枠色だけ
- 根拠: TitleScreen、ChallengeIntro、ArrivalOverlay、GameResultScreenと共通panel CSS。
- 観察: 白い角丸パネル、濃い枠、中央揃えの説明、黄色ボタンが繰り返される。到着も赤マスも確認ダイアログの印象になる。地図は絵画的で細密、UIは単純なCSSの立体表現で質感の差がある。
- 修正: 基本の文字/色/操作形状は統一しつつ、到着は地名と賞金、危機は目標とリスク、優勝は勝者と代表回答を主役にする構図へ。素材を増やす前に画面別の構成を作る。

## 画面別の目的と判断

| 画面 | してほしいこと | 現状 | 改善の中心 |
|---|---|---|---|
| タイトル | 遊びの魅力を理解して始める | 開始は明確、東京/大喜利/すごろくの関係は遊び方に依存 | コピーとコマ/経路を使い遊びを一目で示す |
| 設定 | 参加者を決めて開始する | 操作は可能だが参加者のまとまりが弱い | 参加者単位の枠、標準設定で開始 |
| 手番開始 | 誰の番か理解し準備してお題を開く | 手動開始は良い、毎回同じ説明が大きい | 色/コマ/名前と「お題を見る」を中心に |
| 回答 | お題を読み15秒で回答する | 入力可能だが表示モード間の位置変化が大きい | お題の位置を安定させ集中を優先 |
| 採点 | 点数と効果を理解し次へ進む | 通常の行動ラベルは良い、長文時の階層は弱い | 点数/効果→回答/講評→主操作 |
| 移動 | 比較して進路を確定する | A/B/Cだけでは判断不足 | 選択前から距離/マス種別を提示 |
| 全体地図 | 現在地と目的地の関係を見る | 縦の余白とラベル重なり | 専用の縮尺・ラベル・カメラ操作 |
| 青/赤マス | 報酬/リスクを理解して挑戦 | 赤は抽象説明が重複、具体目標は開始後 | 説明を短くし、目標発表時の強調を設計。事前開示はゲーム仕様判断として分離 |
| 到着 | 達成と賞金を喜び次へ進む | 次操作は明確、祝う表現は弱い | 街の見せ場、賞金の主役化 |
| 最終順位 | 勝者と面白かった回答を振り返る | 順位は明快、回答は折り畳み、主操作は退出 | 代表回答を見せ、再戦を検討 |

## 維持したい点

手動でお題を開く、回答送信と移動確定を明示する、通常採点後の「○マス進む！」、色と番号を併用する、金額の前後を示す、長文部分を独立スクロールする設計は有用。これらを捨てて全面的に装飾だけを作り直す必要はない。

## 推奨する順序

1. 移動と全体地図の判断支援を設計。
2. 回答・採点を安定した縦画面フローとして再構成。
3. 設定を参加者中心に整理。
4. 到着/危機/優勝それぞれの構図と表現を作る。
5. 共通部品の質感を統一し、iPhone実機で初見操作を確認。

自動テスト成功は操作・見た目の使いやすさの合格とは区別する。本レビューは観察と設計判断であり、ユーザーの成功率を測定した結果ではない。
